# ADR 0070: Cross-Origin Requests (CORS)
Status: Accepted and implemented (2026-11-06; see Implementation notes), after one-decision-at-a-time review: §1
accepted, to be revisited after alpha item 5; §2 revised (methods from
the routes, request headers echoed, a refused preflight is 403), stating a
general principle (charter principle 10); §3, §4, §7, §8, and §9 accepted
as drafted, with notes; §5 accepted with no `Vary` under `*`; §6 revised
from two hours to 30 minutes.
Date: 2026-11-04
Related: ADR 0027 (deployment configuration), ADR 0069 (headers, cookies,
content types; open question 6 is this ADR), ADR 0051 (no warnings),
alpha item 5 (configuration from the environment).

## Context

A browser runs a page from one origin (`https://app.example.com`) and
lets its script call a service on another (`https://api.example.com`)
only if the service says so. The scheme, host, and port together make the
origin, so `http://localhost:5173` calling `http://localhost:8080` is
cross-origin too. That is the everyday shape of local front-end
development.

The browser asks in one of two ways:

- **A simple request** (GET, HEAD, or a POST with a form or `text/plain`
  body, and only safelisted headers) is sent as is, with an `Origin`
  header. The browser hands the response to the script only if it carries
  `Access-Control-Allow-Origin` naming that origin.
- **Anything else** is preceded by a preflight: an `OPTIONS` request with
  `Origin`, `Access-Control-Request-Method`, and
  `Access-Control-Request-Headers`. The real request is sent only if the
  answer allows that method and those headers.

Every fiig request with a body needs a preflight. `consumes
"application/json"` isn't a safelisted type, and neither are `PUT`,
`PATCH`, `DELETE`, or `QUERY`, nor any header a route reads with `from
header`, such as `Authorization`.

Today a fiig service answers neither. `OPTIONS` isn't a route verb, so a
preflight gets 404, and nothing writes `Access-Control-*` headers.
Since ADR 0069 §6 refuses no such header, a program could set
`Access-Control-Allow-Origin` itself, but it can't answer the preflight,
so only simple requests would get through.

**What frameworks do.** Every framework makes CORS a middleware or
setting, not something each handler writes:

| Framework | Off by default | Where origins come from | Methods allowed | Request headers allowed | Credentials |
|---|---|---|---|---|---|
| Express `cors()` | no: `*` when added bare | code | written out | written out, or echo the request (default) | off unless set |
| Go `rs/cors` | n/a (opt in) | code | written out, defaults GET/POST/HEAD | written out | off unless set |
| Spring `@CrossOrigin` | yes | annotation or config | the handler's own mappings | any (`*`, default) | off unless set |
| ASP.NET Core | yes | named policy in code | written out | written out | off unless set |
| Django `django-cors-headers` | yes | settings | written out | a default list | off unless set |
| Rails `rack-cors` | yes | initializer | written out | written out | off unless set |

Two things stand out. Spring's `@CrossOrigin` derives allowed methods from
the handler's mappings, because it already knows them. Everyone else makes
the programmer write the list a second time. No framework derives request
headers, since a handler can read any header at run time; Spring allows
any. Spring answers a refused preflight with 403. The mistakes CORS
guides warn about are also the same everywhere:

- reflecting any `Origin` back with credentials on, which lets every site
  act as the user;
- forgetting `Vary: Origin`, so a cache serves one origin's answer to
  another;
- trusting `Origin: null`, which sandboxed iframes and `file:` pages
  send;
- matching origins by suffix or regex (`evil-example.com` passes
  `endsWith("example.com")`).

A fiig route already declares its verb, path, the headers it reads, and
whether it reads a cookie (ADR 0069 §1). That is most of what a CORS
policy says.

## Decision

### 1. Origins are deployment configuration, off by default

The adapter allows no cross-origin calls unless `fiig serve` is given
origins to allow:

```
fiig serve -allow-origin https://app.example.com -allow-origin http://localhost:5173 . api
ALLOW_ORIGINS=https://app.example.com,http://localhost:5173 fiig serve . api
```

`-allow-origin` may be repeated. Without it, the server reads
`$ALLOW_ORIGINS` (comma-separated), the way `-addr` falls back to
`$LISTEN_ADDR`. Without either, CORS is off: no `Access-Control-*`
header is ever written, and a preflight gets 404 as today.

Origins live outside the source because they change per environment while
the program doesn't. The same build serves `localhost:5173` in
development and `app.example.com` in production. Code-based frameworks
read this list from a setting for the same reason.

Each origin is checked when the server starts, and a bad one stops it,
the way an unset `${NAME}` in the capabilities file does:

- It must be `scheme://host` or `scheme://host:port`, with `http` or
  `https`, and no path, query, or trailing slash. This is the exact form a
  browser sends.
- It is compared exactly, after lowercasing the scheme and host, with no
  suffix or pattern matching.
- `null` is refused, since anything sandboxed can send it.
- `*` (alone) allows every origin without credentials (§3).

**Revisit after alpha item 5.** Owner's decision in review: this placement
holds for now, and is reconsidered once fiig code can read configuration
from the environment. At that point the list could move into the source
(Alternative A) with its values still supplied per environment.

### 2. Methods come from the routes; request headers are echoed

The adapter answers a preflight itself, from the route table:

- **Path.** The preflight's path is matched the way a request is. If no
  route has that path, the answer is 404.
- **Method.** `Access-Control-Allow-Methods` lists the verbs of the
  routes at that path. A method is a statement about the service, and
  fiig knows the true answer, so it isn't written down a second time.
- **Headers.** `Access-Control-Allow-Headers` echoes the names the
  preflight asked for in `Access-Control-Request-Headers`, each of which
  must be an HTTP token. A header is a statement about the client: a route
  still reads only the headers it names with `from header` (ADR 0069
  §1), and any other header is inert. Browser SDKs add their own
  (OpenTelemetry's `traceparent`, Sentry's `sentry-trace` and `baggage`),
  and refusing them would break a front end for nothing.
- **Refused.** If the origin isn't allowed, the requested method isn't
  among the routes, or a requested header name isn't a token, the answer
  is 403 with no `Access-Control-*` headers. The browser blocks the call
  either way; a 403 is easier to see in a network tab or with `curl`.

`OPTIONS` stays out of the route grammar. The adapter owns it, the way it
owns `Content-Type`.

This split is a general fiig principle, stated by the owner in this
review and recorded as charter principle 10: **fiig is strict about what
the program says and reads, and lenient about extra things it receives and
ignores.** ADR 0062 §2 (a JSON `3.0` read as an int) is an earlier case.
The one cost here is that a misspelled *optional* header reads as `None`
without an error, but `curl` does the same, so it isn't CORS's to fix.

### 3. Credentials follow the origin list

Credentials here mean cookies and HTTP authentication the browser adds
itself, not an `Authorization` header the script writes. A bearer token
needs no credentials mode.

- **Listed origins.** Each one gets `Access-Control-Allow-Credentials:
  true`. Listing an origin already says it may act for the user, and
  credentials are the only way a cookie session (ADR 0069 §4) works
  across origins.
- **`*`.** It never sends credentials, and the browser wouldn't accept
  them with `*` anyway. It is a startup error if any route in the adapter
  reads a cookie, since that route could never work from a browser on
  another origin.

No framework surveyed turns credentials on by default. Their default
guards against reflecting any origin with credentials on; §1 makes that
impossible, since only exactly listed origins pass. The `*` check sees
only routes that *read* a cookie. A route that only sets one does so at
run time, and under `*` the browser discards it. That gap is accepted:
a useful cookie is read by some route, and that route trips the check.

### 4. Exposed headers come from each response

By default a script on another origin can read only the safelisted
response headers (`Cache-Control`, `Content-Type`, and a few others). On
an allowed origin, every response lists the headers it actually set in
`Access-Control-Expose-Headers`. A program that sets `Location` or
`Retry-After` doesn't have to say so twice.

Headers every script may already read (`Cache-Control`,
`Content-Language`, `Content-Length`, `Content-Type`, `Expires`,
`Last-Modified`, `Pragma`) are left out, and `Set-Cookie` never appears,
since browsers never let a script read it. A preflight answer doesn't
carry this header.

This list is per response rather than a fixed one. ADR 0069 §8 notes
that a response's headers come from a run-time `Map`, so no fixed list
could be derived. The `*` form isn't used, because browsers ignore it on
credentialed responses.

### 5. `Vary` is always correct

With listed origins, every response carries `Vary: Origin`, including
responses to disallowed origins and to requests with no `Origin` at all.
The answer depends on the origin, so a shared cache must key on it.
Otherwise a CDN can hand one listed origin a response naming another, or
hand a browser a copy cached for a request with no `Origin` and no CORS
headers. Middleware that adds `Vary: Origin` only when the request has an
`Origin` leaves that second case open.

A preflight answer also varies on `Access-Control-Request-Method` and
`Access-Control-Request-Headers`. If the program's response sets its own
`Vary`, the adapter adds `Origin` to it rather than replacing it
(`Vary: Accept-Language, Origin`); a program's `Vary: *` is left as is.

Under `*`, every response carries `Access-Control-Allow-Origin: *`
whatever the origin, so nothing varies and no `Vary` is added. With CORS
off, nothing is added either.

### 6. The preflight answer is cached for 30 minutes

`Access-Control-Max-Age: 1800`, Spring's value, with no setting. Without
the header browsers reuse an answer for 5 seconds; Chromium caps it at two
hours and Firefox at a day.

A longer value buys less than it seems, because the cache is per URL, not
per route: `/accounts/1` and `/accounts/2` are separate entries. And it
costs revocation time. A browser holding a cached answer for an origin
that has since been removed from the list still *sends* its non-simple
requests, cookies included, until the answer expires; the service runs
them, and only the response is hidden. So removing an origin stops its
writes within 30 minutes, not at once. If revocation must be immediate,
the fix is to invalidate the sessions, not the origin list. A setting
would only let a deploy choose a longer window without seeing that cost.

### 7. The adapter owns `Access-Control-*`

ADR 0069 §6's adapter-owned headers gain every name starting
`Access-Control-`. Setting one is W1: a checker error on a constant, a
fault otherwise. A program can't open what deployment configuration
closed.

Letting the program's value win would let one response reopen a service
whatever the origin list says, including one with CORS off, and
contradict the adapter's own headers. `httpspec.AdapterOwnedHeader`,
which the checker and the adapter both call, gains the prefix
(case-insensitive), and the W1 message says the adapter writes these from
`fiig serve -allow-origin`.

`Vary` stays the program's (§5 merges into it), and a route may still
read `from header "Origin"`, for logging say: by the time the workflow
runs the adapter has already decided.

### 8. Errors carry CORS headers too

On a request from an allowed origin, every real response carries the
same CORS headers (§3 to §5), whatever its status: what a workflow
produced (a 401 challenge, a 409, a 404 from a mapping), the adapter's
own refusals (a 400 for a missing header or an undecodable body, a 415, a
404 for a path no route has), and a 500 fault, including a W1 or W2
refusal. Exposed headers (§4) list what that response set. Without them
the browser hides the response, and the front end sees only "Failed to
fetch", the same as a server that is down, where the service gave a
reason.

The adapter decides the CORS headers once, from the request's `Origin`,
before routing, and every write path uses them. That is the bug this
prevents: in several frameworks error handling runs outside the CORS
layer or clears headers already set (ASP.NET Core's exception handler
clears them), and "errors show up as CORS failures" is among the most
common CORS questions. The one exception is §2's refused preflight, which
stays bare, since CORS headers on it would contradict it.

A fault's 500 body carries its message, as it does today, so scripts on
listed origins now see it too; they are trusted, and `curl` already sees
it. Whether fault messages reach clients at all is open question 3.

### 9. Scope

- **One policy per adapter.** There are no per-route origins. `fiig
  serve` serves one adapter, so its flags already apply to exactly one; a
  service whose routes need different origins can be split into two
  adapters, served as two processes.
- **Not in this ADR:**
  - wildcard subdomains (`https://*.example.com`), for per-tenant front
    ends. If a real app needs them, they come as a strict pattern
    matching one DNS label, never a suffix or a regex;
  - Private Network Access preflights
    (`Access-Control-Request-Private-Network`), which Chrome has moved
    to a permission prompt shown to the user;
  - an origin list readable from fiig code (alpha item 5's concern).
- **Cookies across sites.** CORS works across *origins*, but `SameSite`
  works across *sites*. `app.example.com` and `api.example.com` are one
  site, so ADR 0069's `Lax` default works between them. A front end on a
  different site needs `sameSite: SameSite.AnySite`, and browsers
  increasingly block such third-party cookies regardless. The docs will
  recommend one site with two hosts, or else a bearer token in
  `Authorization`, which needs no cookies or credentials.
- **Unchanged:** `cli` adapters, OpenAPI, and the route grammar.

## Alternatives considered

**A. Origins in the source**, as an adapter clause (`allows origins
"https://app.example.com"`). It is visible to the checker and the
catalog. Rejected for §1's reason: the list differs per environment, so
the source would need environment values, which is alpha item 5 and not
built yet. It can be revisited once item 5 exists, since the routes
already supply everything else.

**B. Methods and headers written out**, as Express and ASP.NET do. This
is more explicit, but it duplicates what the route already says, and the
two drift apart. Spring's derivation is the precedent.

**C. Derive request headers too.** Allow only the `from header` names of
the routes at that path. This was §2's first draft. It makes a misspelled
header a preflight failure in the browser's console. Rejected in review:
it refuses headers browser SDKs add on their own, so adding Sentry or
OpenTelemetry to a front end would break every call, and the only fix
would be a workflow parameter nobody reads. A misspelled required header
already gets a 400 naming it.

**C2. Echo methods too.** Rejected: it would claim the service accepts a
verb no route has.

**D. A separate credentials switch.** Rejected for §3's reason: an
exact-listed origin is already trusted, and the switch's only use would
be to turn off cookie sessions that a route reading a cookie needs.

**E. Leave it to a reverse proxy.** The owner ruled this out in ADR
0069's review. A proxy also can't see which headers each route reads, so
it would need its own copy of §2.

## Consequences

- Front-end development against `fiig serve` works with
  `-allow-origin http://localhost:5173` and nothing in the source.
- A deploy that forgets the flag fails closed: the browser refuses the
  calls, and the service behaves as it does today.
- ADR 0069's 415 already blocks the classic cross-site form POST against
  a JSON route, since a form can't send `application/json`. A route that
  `consumes "text/plain"` can still be posted to from any site without a
  preflight, as with every framework. CORS doesn't change that, because
  CORS only decides who may *read* the response.
- OpenAPI is unchanged; CORS isn't part of the API description.

## Implementation notes (2026-11-06)

Built in three steps: §7's W1 (`httpspec.AdapterOwnedHeader` now says
where the adapter takes each owned header from, and both the checker and
the adapter quote it), the CORS layer (`compiler/adapter/cors.go`:
`ParseOrigins` and `WithCORS`), and `fiig serve -allow-origin`. Dogfooded
against `examples/accounts` with `-allow-origin http://localhost:5173`.
Decisions made while building, beyond the text above:

- **A path is matched by asking the router.** A preflight probes the
  adapter's `ServeMux` once per verb the adapter uses, so the allowed
  methods are exactly the routes that would serve that path. `/items/{id}`
  and `/items/{key}` are one path, and a more specific route (`/items/new`)
  is handled the way the real request would be.
- **A scheme's default port is refused** (`https://app.example.com:443`):
  browsers leave it out of `Origin`, so the listed origin would never
  match. The error gives the spelling to use.
- **Not exposed (§4):** `Vary`, which the adapter merges, and the
  `X-Content-Type-Options: nosniff` Go's own 404 and 405 add. Neither is
  a header the program set.
- **A plain `OPTIONS`** (no `Origin`, or no `Access-Control-Request-Method`)
  isn't a preflight and goes to the router as before.
- **Startup log.** `fiig serve` logs the origins it allows, which settles
  open question 2: a deploy can see that `$ALLOW_ORIGINS` was read.
- **Preflight `Vary`** lists `Access-Control-Request-Method` and
  `Access-Control-Request-Headers` even under `*`, since the answer
  depends on them whatever the origin.
